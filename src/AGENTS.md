# Plugin source instructions

- Treat the plugin/tool identity, `imagegen` arguments, supported sizes, `{ out, versioned }` result metadata, the `OC_MULTI_IMAGEGEN_BACKEND` and `OC_MULTI_IMAGEGEN_OPENAI_API_KEY` variables and the permission resources (the backend ids) as public contracts. Internal helpers can change in place. Update the README's "Authentication", "Permissions", "Use" and "Current limits" sections when documented behavior changes.
- One default export serves OpenCode 1 (`server`, `v1.ts`) and OpenCode 2 (`setup`, `v2.ts`). Both adapters stay thin: they call `selectBackend`, then supply the permission request, session directory, credential, and cancellation signal to `defineImageTool` in `imagegen.ts` and shape the host's result. Behavior that applies to both hosts goes in the shared flow.
- Import `@opencode-ai/plugin` and `@opencode/plugin` for types only. A runtime import makes the package require an SDK its host may not provide; `tests/unit/index.test.ts` checks this.
- Exactly one backend is active per plugin load, chosen only by `OC_MULTI_IMAGEGEN_BACKEND`, read once when the plugin loads (`backend.ts`); unset means Codex, and a variable that is empty or unknown fails the load without repeating its value. The plugin takes no options: a `backend` option fails the load with the variable to use instead, and an empty or absent options object loads. Plugin settings are namespaced environment variables of the OpenCode process, never plugin options, files or a `.env` loader. Never add a per-call backend argument, credential-driven routing or a fallback to another backend, and register only the tools declared by the active backend. Each tool owns its input schema, description and generation or editing operation; models are selected per call. A backend module (`codex.ts`, `openai-api.ts`) owns its argument spec, request, defaults, limits, reference rules and credential; `imagegen.ts` owns the flow every backend shares. A new backend is a module plus its entry in the one list in `backend.ts`.
- `schema.ts` owns shared argument definitions and the result schema; backend tool definitions own their complete input schemas. Preserve the existing Codex and OpenAI API `imagegen` arguments. Both host adapters register and validate against the same tool schema. Keep `zod` at 4.2 or newer: OpenCode 2 uses the schema's own JSON Schema output only from that version, and otherwise loses the argument descriptions.
- Keep argument and reference-image validation before the tool's `generate` callback; invalid inputs must fail before quota-consuming requests, and bytes that are not a PNG must fail before any directory or file is created. Request the invoked image tool's permission, on the backend's id as resource, before credentials, reference images or the provider are touched. Propagate generation, save, permission and cancellation failures instead of returning a success-shaped result, and do not retry.
- Credentials are read per call, after the permission, and only the entry the active backend names. A key credential's `CredentialSpec` names its one backend-specific variable; credential precedence and isolation apply independently to each backend. When that variable is present it is the credential and the saved key is never consulted, and when it is absent the saved key applies. A present but empty or malformed value fails the call, a provider or host rejection is not retried, and neither falls back to the saved key. Never read `OPENAI_API_KEY`, which can be the chat key, and never affect Codex or its OAuth credential with the variable.
- OpenCode 1 has no public environment resolver, so `auth.ts` reads that variable directly, otherwise `OPENCODE_AUTH_CONTENT` or `auth.json` the way the host resolves them, and never writes, refreshes or reports their contents. OpenCode 2 never reads the key itself: a present variable (checked by presence only) is resolved with `ctx.integration.connection.resolve({ type: "env", name })`, because `active()` lists a saved credential before an environment connection and would return the saved key. Without the variable it reads `active(<provider>)` and resolves that connection. It does not fall back to `auth.ts`, `.env` files or Codex files, and does not refresh tokens in the plugin.
- A key credential belongs to the plugin and is registered natively: an `auth` hook with an `api` method and no loader on OpenCode 1; on OpenCode 2 a `ctx.integration.transform` entry with a `key` method and an `env` method that names only that variable. Never add a provider or model entry for it (it takes part in OpenCode's default chat model choice), and never activate or change the chat credentials. The OpenAI ChatGPT sign-in used by Codex belongs to the host.
- `skills/oc-multi-imagegen/SKILL.md` is the one authored copy of the image-technique guidance; `skill.ts` reads it for both hosts (OpenCode 1 adds the absolute `skills/` directory to `skills.paths` in its `config` hook, OpenCode 2 registers it with `ctx.skill.transform`). Keep the frontmatter to one JSON-string `name` and `description` line, so OpenCode 1's YAML reader and `skill.ts` agree. The skill carries technique only; arguments, sizes and limits live in the backend modules and `describeImagegen`, which must keep working for an agent that never loads the skill. The plugin never requests a `skill` permission, and a missing or malformed skill file fails plugin load.
