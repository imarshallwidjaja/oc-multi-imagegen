# Plugin source instructions

- Treat the plugin/tool identity, `imagegen` arguments, supported sizes, `{ out, versioned }` result metadata, the `backend` plugin option and the permission resources (the backend ids) as public contracts. Internal helpers can change in place. Update the README's "Authentication", "Permissions", "Use" and "Current limits" sections when documented behavior changes.
- One default export serves OpenCode 1 (`server`, `v1.ts`) and OpenCode 2 (`setup`, `v2.ts`). Both adapters stay thin: they read the `backend` option, then supply the permission request, session directory, credential, and cancellation signal to `generateImage` in `imagegen.ts` and shape the host's result. Behavior that applies to both hosts goes in the shared flow.
- Import `@opencode-ai/plugin` and `@opencode/plugin` for types only. A runtime import makes the package require an SDK its host may not provide; `tests/unit/index.test.ts` checks this.
- Exactly one backend is active per plugin load, chosen only by the `backend` plugin option (`backend.ts`); the default is Codex. Never add a per-call backend argument, credential-driven routing or a fallback to another backend, and register one `imagegen` definition whose schema, defaults and description belong to the active backend. A backend module (`codex.ts`, `openai-api.ts`) owns its argument spec, request, defaults, limits, reference rules and credential; `imagegen.ts` owns the flow every backend shares. A new backend is a module plus its entry in the one list in `backend.ts`.
- `schema.ts` owns the shared argument shape and the result schema; a backend fills in the size, reference limit and guidance that differ. OpenCode 1 consumes the shape and OpenCode 2 the object schema. Keep `zod` at 4.2 or newer: OpenCode 2 uses the schema's own JSON Schema output only from that version, and otherwise loses the argument descriptions.
- Keep argument and reference-image validation before `backend.generate`; invalid inputs must fail before quota-consuming requests, and bytes that are not a PNG must fail before any directory or file is created. Request the `imagegen` permission, on the backend's id as resource, before credentials, reference images or the provider are touched. Propagate generation, save, permission and cancellation failures instead of returning a success-shaped result, and do not retry.
- Credentials come from OpenCode's own store, per call, and only the entry the active backend names. OpenCode 1 reads `OPENCODE_AUTH_CONTENT` or `auth.json` in `auth.ts` the way the host resolves them, and never writes, refreshes or reports their contents. OpenCode 2 reads `ctx.integration.connection.active(<provider>)` and resolves that connection; it does not fall back to `auth.ts`, environment variables, `.env` files or Codex files, and does not refresh tokens in the plugin.
- A key credential belongs to the plugin and is registered natively: an `auth` hook with an `api` method and no loader on OpenCode 1, a key-only `ctx.integration.transform` entry on OpenCode 2. Never add a provider or model entry for it (it takes part in OpenCode's default chat model choice), and never activate or change the chat credentials. The OpenAI ChatGPT sign-in used by Codex belongs to the host.
- `skills/oc-multi-imagegen/SKILL.md` is the one authored copy of the image-technique guidance; `skill.ts` reads it for both hosts (OpenCode 1 adds the absolute `skills/` directory to `skills.paths` in its `config` hook, OpenCode 2 registers it with `ctx.skill.transform`). Keep the frontmatter to one JSON-string `name` and `description` line, so OpenCode 1's YAML reader and `skill.ts` agree. The skill carries technique only; arguments, sizes and limits live in the backend modules and `describeImagegen`, which must keep working for an agent that never loads the skill. The plugin never requests a `skill` permission, and a missing or malformed skill file fails plugin load.
