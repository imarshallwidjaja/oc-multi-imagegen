# Plugin source instructions

- Treat the plugin/tool identity, the `imagegen` and `imageedit` arguments (including `preview` and the OpenAI `mask`), supported sizes, `{ out, versioned }` result metadata and OpenCode 2's `{ out, versioned, message }` output, the OpenCode 2 Code Mode paths (`image`, or `image.<backend id>` with `-` written as `_` when several backends load), the `OC_MULTI_IMAGEGEN_BACKEND` and `OC_MULTI_IMAGEGEN_OPENAI_API_KEY` variables, OpenCode 2's `backend`/`backends` plugin options, the permission actions (bare tool names) and resources (the backend ids), and the `webfetch` permission for reference URLs as public contracts. Treat `OC_MULTI_IMAGEGEN_NANOGPT_API_KEY`, NanoGPT model IDs and their documented controls and limits as public contracts. Internal helpers can change in place. Update the relevant topical guides in `docs/` when documented behavior changes; keep the README focused on capabilities and examples.
- One default export serves OpenCode 1 (`server`, `v1.ts`) and OpenCode 2 (`setup`, `v2.ts`). Both adapters stay thin: they call `selectBackend` (OpenCode 1) or `selectBackends` (OpenCode 2), then supply the permission request, the `webfetch` authorization for reference URLs, session directory, credential, and cancellation signal to the shared flows in `imagegen.ts` (`defineImageTool`; `defineLookupTool` for a provider lookup, which gets no session directory) through `invocation.ts`, and shape the host's result. Only the OpenCode 2 adapter attaches a `preview` as a file part; OpenCode 1 appends a note instead, and neither changes the output or metadata shape. Behavior that applies to both hosts goes in the shared flow. Supply host capabilities lazily: local information tools need no call context, and lookup tools resolve no session directory. Keep OpenCode 2 credential lookup independent of the OpenCode 1 auth-file reader; share only credential policy that performs no file I/O.
- Import `@opencode-ai/plugin` and `@opencode/plugin` for types only. A runtime import makes the package require an SDK its host may not provide; `tests/unit/index.test.ts` checks this.
- Backend selection lives in `backend.ts` and runs once per plugin load. OpenCode 1 runs exactly one backend from `OC_MULTI_IMAGEGEN_BACKEND` (unset means Codex), takes no plugin options (a `backend` option fails with the variable to use; an empty or absent object loads) and refuses `opencode`. OpenCode 2 runs the backends its `backend` or `backends` options select, in order, or the variable's one backend; options and a set variable together fail the load. Load errors name the key or position, never the operator's value. API keys stay in namespaced environment variables or saved integrations, never plugin options, files or a `.env` loader. Never add a per-call backend argument, credential-driven routing or a fallback to another backend, and register only the tools declared by the selected backends. Each tool owns its input schema, description and generation or editing operation; models are selected per call. A backend module (`codex.ts`, `openai-api.ts`, `nano-gpt.ts`, `opencode.ts`) owns its argument spec, request, defaults, limits, reference rules and credential; `imagegen.ts` owns the flow every backend shares. A new backend is a module plus its entry in the one list in `backend.ts`.
- `opencode.ts` has a `host` credential: it generates through `ctx.experimental.generate.image` and lists models through `ctx.model.list`, which `v2.ts` checks at load. It checks the catalog before generating and calls `signal.throwIfAborted()` between lookup and generation because OpenCode 2.3.2 ignores the forwarded signal. The host's own one-shot retries are the only retries; the plugin sends one request.
- `input-image.ts` owns references and the mask. Authorize each URL hop through `authorizeFetch`, one at a time, before fetching it, and send no auth headers. Messages show URLs without query or fragment. A mask must be a PNG with alpha matching `images[0]`'s EXIF-oriented size, checked before any request.
- `schema.ts` owns shared argument definitions and the result schema; backend tool definitions own their complete input schemas. On every backend `imagegen` creates from text and takes no references, and `imageedit` requires them; each tool selects its own endpoint or operation. Image tool schemas are strict (`strictArgs`): OpenCode 2 validates input against the schema before `execute`, so a stripped argument such as `images` on `imagegen` would otherwise vanish silently instead of failing. Both host adapters register and validate against the same tool schema. Keep `zod` at 4.2 or newer: OpenCode 2 uses the schema's own JSON Schema output only from that version, and otherwise loses the argument descriptions.
- An image tool declares its operation and output formats. Edit schemas require `images`, and the shared flow owns loading those references. Validate arguments, credentials and references before the tool's `request` callback. Invalid inputs must fail before quota-consuming requests. Providers return native bytes decoded at the response boundary after validating the wire value; output saving accepts only the tool's declared formats. Save native bytes without conversion, with an extension matching the detected format, and return the actual saved path. Detect the format and finite positive header dimensions, or for SVG pass `svg.ts`'s static-vector check and root geometry, before creating any directory or file; reject unsupported types and unreadable or invalid dimensions without exposing provider payloads. Header inspection is not full corruption decoding, and the SVG check is a refusal check, not a sanitizer. Set `versioned` only for a collision's `-vN` suffix, not an extension adjustment. `png-alpha.ts` and `image-format.ts` own the PNG and WebP alpha inspection; `output-image.ts` owns the warning for a confirmed opaque PNG after `background: "transparent"` and preview handling. `preview` never reaches a provider. Request the invoked tool's permission, on the backend's id as resource, before credentials, reference images or the provider are touched; only a local information tool needs none. Propagate generation, save, permission and cancellation failures instead of returning a success-shaped result, and do not retry.
- Credentials are read per call, after the permission, and only the entry the active backend names. A key credential's `CredentialSpec` names its one backend-specific variable; credential precedence and isolation apply independently to each backend. When that variable is present it is the credential and the saved key is never consulted, and when it is absent the saved key applies. A present but empty or malformed value fails the call, a provider or host rejection is not retried, and neither falls back to the saved key. Never read `OPENAI_API_KEY`, which can be the chat key, and never affect Codex or its OAuth credential with the variable.
- OpenCode 1 has no public environment resolver, so `auth.ts` reads that variable directly, otherwise `OPENCODE_AUTH_CONTENT` or `auth.json` the way the host resolves them, and never writes, refreshes or reports their contents. OpenCode 2 never reads the key itself: a present variable (checked by presence only) is resolved with `ctx.integration.connection.resolve({ type: "env", name })`, because `active()` lists a saved credential before an environment connection and would return the saved key. Without the variable it reads `active(<provider>)` and resolves that connection. It does not fall back to `auth.ts`, `.env` files or Codex files, and does not refresh tokens in the plugin.
- A key credential belongs to the plugin and is registered natively: an `auth` hook with an `api` method and no loader on OpenCode 1; on OpenCode 2 a `ctx.integration.transform` entry with a `key` method and an `env` method that names only that variable. Never add a provider or model entry for it (it takes part in OpenCode's default chat model choice), and never activate or change the chat credentials. The OpenAI ChatGPT sign-in used by Codex belongs to the host.
- `skills/oc-multi-imagegen/SKILL.md` is the one authored copy of the image-technique guidance; `skill.ts` reads it for both hosts (OpenCode 1 adds the absolute `skills/` directory to `skills.paths` in its `config` hook, OpenCode 2 registers it with `ctx.skill.transform`). Keep the frontmatter to one JSON-string `name` and `description` line, so OpenCode 1's YAML reader and `skill.ts` agree. The skill carries technique only; arguments, sizes and limits live in the backend modules and the tool descriptions (`describeGenerationTool`, `describeEditTool`), which must keep working for an agent that never loads the skill. The plugin never requests a `skill` permission, and a missing or malformed skill file fails plugin load.
