# Unit test instructions

- Keep unit tests independent of real credentials and provider access. OpenCode 1 `execute` tests use synthetic `OPENCODE_AUTH_CONTENT`; OpenCode 2 tests use the fake plugin context in `hosts.ts`, whose connection store answers per integration id, where `active` returns only the saved connection and an environment key is resolved by name; direct `backend.generate` tests pass fake credentials explicitly. All stub `globalThis.fetch`.
- Put behavior both hosts and both backends share in `imagegen.test.ts`, which runs each case against both adapters with each backend selected, through `hosts.ts`; that includes which source the image API key comes from. Put host-specific behavior (permission request shape, how a credential is looked up, native sign-in registration, result shape, registration) in `v1.test.ts` or `v2.test.ts`, backend and option selection in `backend.test.ts`, and each backend's exact request, arguments and limits in `codex.test.ts` or `openai-api.test.ts`; do not repeat shared cases there.
- Select a backend with `selectBackendVariable` in `hosts.ts`, the way a deployment does, never through plugin options. Call `isolateEnvironment()` from `fixtures.ts` in every file that loads the plugin or reads a credential: test files share a Bun process, and it sets aside, unsets and restores `OPENCODE_AUTH_CONTENT`, `OC_MULTI_IMAGEGEN_BACKEND` and `OC_MULTI_IMAGEGEN_OPENAI_API_KEY` without printing or exposing inherited values. Restore `globalThis.fetch` after tests that change it.
- For auth-file tests, follow `auth.test.ts`'s temporary path and `mock.module("xdg-basedir", ...)`. `xdg-basedir` caches `XDG_DATA_HOME` at first import, so changing that environment variable later does not redirect auth reads.
- Key-source tests use distinct synthetic keys for the variable and the saved credential, so a request's `Authorization` header shows which one was used.
- `container.test.ts` runs `scripts/` as subprocesses against synthetic auth files and dotenv files in temporary directories and a fake `docker` on `PATH`. The fake `docker` never runs the script a container would, so the in-container probes (`container-skill-probe.sh`, `container-backend-probe.sh`) are run directly with a fake `opencode` and `wget`. It needs Bash, POSIX `sh`, GNU `timeout`, `base64` and Bun, and never real Docker, credentials or paid calls. Keep each safeguard (sandbox checks, seed refusal, container stop and unconfirmed stop, seed ownership, stale-work refusal, the probes' failure cases) tested there once.
- `index.test.ts` packs the repository with `npm pack`, extracts the tarball with `tar`, and uses `Bun.build` to bundle the entry point into the extracted copy, to resolve the skill the way an installed package does. It needs both commands on `PATH` and no earlier `bun run build`, network or credentials.
